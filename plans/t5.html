Financial & Transaction Controls

Separate Sales vs After-Sales invoicing, estimate lifecycle with human numbering, reversible ready-for-pickup gate, and immutable lock after final approved invoice — one shared line-item builder, audit everywhere, no PDF redesign.

t5 TanStack Start · Convex · Zod Finance-owned

Requirement → Design Decisions

1 — Invoices: domain + kind + nullable linkage + human numbers

  • Schema: domain:'service'|'sales', kind:'estimate'|'final', jobId?: Id<jobs>, salesOrderId?: Id<salesOrders>, invoiceNumber: string (EST-YYYY-#### / INV-YYYY-####), locked: boolean, generatedById?: Id<users>, status:'draft'|'approved'|'rejected' for estimate workflow, rejectedReason?. Keep legacy approved boolean for migration then derive from status.
  • Nullability rule: domain==='service' ⇒ jobId required, salesOrderId undef; domain==='sales' ⇒ salesOrderId required, jobId undef. Enforced in mutations (Zod + runtime check), not at schema validator level to keep old rows migratable (existing rows backfilled as service/final via migration helper).
  • Indexes: keep by_jobId (existing jobId index becomes sparse), add by_salesOrderId + by_invoiceNumber. Domain/kind filtered in-memory or via compound index if frequent.
  • Settings counters doc: extend single settings row with nextEstSeq:number, nextInvSeq:number, estYear:number, invYear:number. Numbering helper nextInvoiceNumber(kind, ctx) reads settings, resets if year !== storedYear, increments atomically (Convex serializes mutations; OCC via single doc read-modify-write).
  • Shared line-item builder: extract convex/lib/invoiceHelpers.ts — buildLineItemsForJob(ctx, jobId) and buildLineItemsForSalesOrder(ctx, salesOrderId) both call inner describeJobItems() that resolves part.code - description / labourType.name exactly once. Compute totals via existing computeInvoiceTotals(lineItems, vatRate). Kill duplication in invoices.generate / regenerate + seedAdvanced.

2 — Estimates lifecycle (CSR prepares; Finance/Manager/Admin governs)

MutationAllowed rolesGate
invoices.createEstimatecsr,manager,adminjob must exist; jobItems ≥1; creates domain=service, kind=estimate, status=draft, locked=false, invoiceNumber=EST-...
invoices.updateEstimatecsr,manager,admin (owner CSR or manager/admin)Only when kind=estimate && status=draft && !locked. Rebuilds lineItems via shared helper or explicit edits; does NOT bump number. Outside edit window → throw.
invoices.approveEstimatefinance,manager,adminEstimate draft → approved. Keeps locked=false (estimates never lock).
invoices.rejectEstimatefinance,manager,adminRequires reason:string[3..300], sets status=rejected + audit.
invoices.convertEstimateToFinalfinance,manager,adminApproved estimate → new or mutated kind=final invoice with invoiceNumber=INV-..., copies lineItems totals, sets generatedById=currentUser, locked=false until approved (see #4).
Spec says estimate edit window — treat as status-gated not time-gated (simpler, auditable). Rejecting also ends window. No auto-expiry; time window would require cron + drift.
Sales domain nuance: Sales estimates/invoices built from salesOrderId: single line item = vehicle description (make model year plate) ×1 at agreedPrice. Sales estimates reuse same lifecycle but created by salesRep, manager, admin via createSalesEstimate variant sharing helper.

3 — Reverse ready-for-pickup

  • jobs.reverseReady — requireRole(['manager','admin']) only. Guard: job.status==='readyForPickup' AND no approved final invoice exists for that job (query invoices where jobId==jobId && kind==final && approved==true). If locked final exists → throw “Cannot reverse after final invoice approved”.
  • Patch: status:'inProgress', clear readyForPickupTs (set undefined), set inProgressTs keep original, add reversedReadyTs:Date.now() optional field. Audit job.reverseReady.

4 — Lock after final invoice approved

  • When kind==='final' && approved===true → locked=true + generatedById=currentUserId (+ approvedTs). Set in approve path and in generate when creating already-approved final.
  • Helper assertNotLocked(invoice) throws with ConvexError('Invoice is locked — unlock required') if locked===true.
  • All write paths check: jobs.addJobItem, jobs.removeJobItem, invoices.generate, invoices.regenerate, payments.record (cap), jobs.syncInvoiceForJob (early return if locked). If caller tries to mutate locked job's financials → 403-like ConvexError.
  • invoices.adminUnlock — requireRole(['admin']), args {invoiceId, reason:string[10..300]}, sets locked=false, writes audit with reason (store in auditLogs.action='invoice.adminUnlock:reason'), allowed even when approved.
  • Payments: in record, cap check amount > (grandTotal - amountPaid) → throw “exceeds remaining balance” before insert. Also guard locked already-paid path.

5 — generatedById visibility

  • Query invoices.getByJob / getById returns generatedBy joined user (name/email) only when caller is admin — else null. UI component InvoiceSection renders “Prepared by …” badge only for admin role viewing a final approved invoice.
Scope cuts honored: no COGS recompute, no commissions, no PDF redesign beyond lock + estimate banners (print template adds “ESTIMATE — NOT A TAX INVOICE” watermark when kind==='estimate' and “LOCKED” stamp when locked).

Risks & mitigations

  • Numbering race → single settings doc serializes in Convex; add OCC retry comment. Year rollover missed → store year + reset check.
  • Old invoices lack domain/kind → backfill migration in helper (idempotent, runs on first new mutation).
  • Lock bypass via direct patch → audit + code search: no direct ctx.db.patch('invoices') outside guarded helpers; all paths call assertNotLocked.
  • Permission matrix drift → table above is source of truth; each mutation's requireRole array matches spec plus admin bypass already in isAuthorized.
  • T3 concurrent branch collision → final merge keeps both schema.ts + enums.ts additive sides; never delete totp/session fields.
  • RAM tight → one heavy command at a time; pc check before build.

Break-it tests (exhaustive, click-through)

Functional — estimates

  • Login CSR (amara@… / password123) → job with items → Create Estimate succeeds, shows EST-YYYY-####, status draft.
  • CSR edits draft estimate line rebuilds after adding job item → totals update, number unchanged.
  • CSR tries edit after approve → throws “Estimate no longer editable”.
  • Finance approves estimate → status approved.
  • Finance rejects draft estimate with reason → status rejected, reason visible; further edits blocked.
  • Finance converts approved estimate → new or mutated final invoice INV-YYYY-####, totals copied, generatedById set.
  • Non-finance (csr, salesRep) calling approve/reject/convert → unauthorized error.
  • Sales estimate path: salesRep creates estimate for salesOrder → number EST-YYYY, domain sales.
  • Regenerating a locked final → throws locked. Regenerating a draft estimate → succeeds.

Reverse ready

  • Manager/Admin on job in readyForPickup with no approved final → Reverse succeeds, status back to inProgress, audit + timestamp.
  • Manager tries reverse when approved final exists → throws “Cannot reverse after final invoice approved”.
  • CSR / finance / inventoryManager calling reverse → unauthorized.
  • Reverse on job not in readyForPickup → throws transition error.

Lock enforcement

  • Create final, approve as finance → invoice becomes locked=true, UI shows LOCKED banner, generatedBy visible only to admin.
  • While locked: addJobItem → throws, removeJobItem → throws, payments.record beyond balance → throws before insert, regenerate → throws.
  • syncInvoiceForJob called while locked → no-op (invoice totals frozen).
  • Non-admin calling adminUnlock → unauthorized. Admin without reason (<10 chars) → Zod reject.
  • Admin unlock with reason → locked=false, audit entry contains reason, subsequent addJobItem succeeds, re-approve re-locks.
  • Payments cap: record payment > remaining balance → throws (even when not locked).
  • Human numbering: create 3 estimates same year → EST-2026-0001, 0002, 0003; create 2 finals → INV-2026-0001, 0002; year rollover resets.

Regressions / cross-cutting

  • Existing jobItems flow unchanged for jobs without invoices.
  • PrintableInvoice shows estimate watermark vs locked stamp.
  • SeedAdvanced idempotent; legacy invoices backfilled to service/final with legacy number if missing.
  • Every new mutation writes auditLogs; audit visible in DB.
  • No mocked frontend data — queries hit Convex directly.
