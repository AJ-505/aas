CMA · T7 · Enable throttling — client review

Throttling that never blocks a real shift, but always shows the checkbox ticked.

Single-tenant staff app (≤10 users). No middleware, no Redis, queries cannot write. We enforce after requireRole with aligned-window counters (one doc per user:class:window, composite index). Generous windows, kill-switch ON by default, structured RATE_LIMITED/DEDUP errors, and a visible admin log.

10 Decisions (synthesis)

  1. Mechanism: lazy windowStart=floor(ts/w)*w — new doc per window, no reset patch, no scheduler on hot path. @convex-dev/rate-limiter is ideal but fallback is this table (OCC-safe).
  2. Coverage: EVERY public mutation gets enforce() AFTER auth; queries never limited (document why).
  3. Classes: admin 5/min financial 20/min bulk 5/min standard 60/min
  4. Default: ships ENABLED + settings.rateLimitEnabled kill-switch (admin-only).
  5. Errors: ConvexError({code:'RATE_LIMITED', retryAfterMs}) + DEDUP for double-submit.
  6. Observability: rateLimitEvents + audit rateLimit.hit:* + /admin Throttle tab.
  7. GC: daily cron prunes events >30d, windows >24h.
  8. Auth honesty: signIn/reset are HTTP routes — no IP in mutations; per-user limit after auth + client isPending debounce; document limitation.
  9. Dedup: payments.record 60s identical fingerprint guard.
  10. Tests: unit helper + kill-switch + window roll, no mocked DB — real Convex tables.
key = `${userId}:${class}` · windowStart = floor(now/60000)*60000 · index by_key_window · throw {code, retryAfterMs} · audit before throw

Risk before / after

Before: unlimited writes — stray double-click or CSV loop can double-pay / double-reserve.
After: bounded throughput with generous caps; busy shift never hits 60/min CRUD, finance never hits 20/min except runaway script.
Structured errors: toast “Too many requests — retry in 12s” vs business error. No silent drops.

Break-it tests

Unit — lib/rateLimit.test (convex-test style)
  • Window aligned: ws = floor(now/60000)*60000
  • First hit inserts count=1; same window increments to 5
  • 6th in 5/min admin window throws RATE_LIMITED {retryAfterMs}, count unchanged
  • Next window rolls to new doc count=1
  • Per-user isolation: A blocked ≠ B; per-class isolation: financial ≠ standard
  • Kill-switch settings.rateLimitEnabled=false → no throw, no writes
  • Dedup: second identical payment <60s → DEDUP; different amount passes; 61s later passes
Integration — per-mutation sample
  • payments.record 20/min financial + 60s dedup; cross-invoice isolation
  • parts.importParts 5/min bulk — 6th within 60s returns RATE_LIMITED before loop
  • customers.create 60/min standard — mixed CRUD still under one bucket
  • users.setRole 5/min admin — 6th throws with retryAfterMs≈windowEnd-now
  • Queries 100× loop never throw, zero rateLimits rows
  • Window roll: advance clock 61s → previously blocked mutation succeeds
Auth surface — honest constraint
Convex Auth signIn/reset are HTTP routes (convex/http.ts + auth.ts Password provider), not Convex mutations — ctx has no ip or headers in mutations. We rate-limit what IS possible: per-user after auth (all app mutations) and normalize any email-keyed limits via trim+lowercase if/when an HTTP wrapper is added. We document that IP limiting inside mutations is unavailable and add client isPending debounce on login instead. Future HTTP wrapper can add x-forwarded-for IP bucket.
OCC & cost
One index read + one insert/patch per enforce (1 write). Per-user per-window doc avoids hot-row OCC death (single settings doc or global rateLimits/{class} would serialize all writers). Window roll is a new doc → no contended reset patch. Kill-switch short-circuits to one cached settings read, zero writes.
