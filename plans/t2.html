Parts Catalogue Upgrade

Rename Code → Part Number UI-only, add brand + category to parts, introduce vehicleBrands CRUD + brand-aware pickers, and ship filtered search on /service/parts. History-safe, backfill-free, demo-seeded.

Design tree & decisions

1) Rename Code → Part Number

Storage stays code UI relabel only

  • Convex field remains parts.code. No migration, invoices/jobItems keep referencing codes by string. History intact.
  • UI labels, table header, form labels, CSV header detection, validation messages say “Part Number”.
  • Mutation layer accepts partNumber as alias for code (Zod + Convex arg normalization) but persists to code. Optional back-compat, no dual-column storage.
  • CSV import recognizes code OR part number / part_number headers; docs strings updated.

2) brand + category on parts

  • Schema: brand?: string, category?: string optional during migration. No required bump. Defaults “Generic” / “Uncategorized” only in seed + UI fallback display (not DB default).
  • Indexes: by_brand and by_category optional, but initial impl filters in-memory (45 rows) to avoid index churn; add indexes only if pagination lands.
  • Zod: brand/category trimmed strings, 1–60 chars, optional. Empty → undefined persisted.
  • Seed: enrich existing 30 + 15 parts with plausible brand/category from prefix map (e.g. OIL→Lubricants/Generic-or-Toyota, BRK→Braking). New installs get values directly.

3) vehicleBrands table

FieldTypeNote
namestringDisplay name exactly as typed
normalizedNamestringlower(trim(name)) for uniqueness check
  • Index by_normalizedName on normalizedName for O(1) dup guard.
  • Mutations: list (query, auth required), create/update/remove with requireRole(['admin','manager']) + audit() + case-insensitive uniqueness (409 via ConvexError).
  • Seed: distinct makes from seed.ts/seedAdvanced.ts + common Nigerian market set (~18 brands). Idempotent: skip if brand table non-empty or brand exists case-insensitively.
  • UI: small admin section on /service/parts (or /admin/brands if cleaner) with list + add/delete; guarded to admin/manager. Picker component BrandSuggestInput uses <datalist> + free-text fallback (no FK enforcement). Same component reused for parts.brand and vehicles.make (sales inventory add/edit).

4) Filtering

  • Backend: extend parts.search args to { q?: string, brand?: string, category?: string }. Empty strings → no filter. Combine with AND. Keep list as unfiltered. Optional new listFiltered query if we want separation—but single search with optional args is simpler.
  • Frontend: in /service/parts add three controls: text search (part number/description), Brand dropdown (All + brands list + free-text?), Category dropdown (All + distinct categories). Debounced combined query via partQueries.search(q, brand, category).
  • Category list derived from distinct parts[].category + static fallback set so filter works even before backfill fully propagated.
Grill objections answered: (1) Don't dual-store code/partNumber—alias at API boundary only. (2) Don't make brand/category required—optional with UI default keeps migration safe for old prod dumps. (3) Brands need normalized uniqueness + audit, not just naive string set. (4) Don't FK-constrain parts.brand/vehicles.make—suggest-only keeps legacy data valid. (5) CSV must stay backward compatible with old “code” headers. (6) Filters must compose (AND) not exclusive.

Build order

  1. Schema + enums — add brand/category to parts, create vehicleBrands table + indexes.
  2. Zod schemas — part.ts add optional brand/category, vehicleBrand schema.
  3. Convex: vehicleBrands.ts — CRUD + seed helper, audit, guards.
  4. Convex: parts.ts — extend search/filter, create/update/import to handle brand/category + code alias, keep requireRole+audit.
  5. Convex: seed.ts / seedAdvanced.ts — backfill brand/category, seed vehicleBrands list.
  6. Frontend queries — add vehicleBrandQueries, extend partQueries.search signature.
  7. UI: /service/parts — relabel Code→Part Number, add Brand/Category inputs + filters, wire BrandSuggestInput, CSV header alias.
  8. UI: /sales/inventory — wire make picker to brands list (free-text fallback).
  9. Docs/ROADMAP — update roadmap row, note storage decision.

Scope cuts respected

  • No price-history, no supplier management.
  • No per-brand logos or images.

Risks & mitigations

  • Brand dup via case → normalizedName index + lower check.
  • Empty brand/category breaks filters → treat empty as “All”, undefined display as Generic/Uncategorized only visually.
  • CSV drift → detect both code & part number headers; brand/category are optional columns with defaults.
  • RAM → verify with typecheck/build only, one heavy command at a time.

Break-it tests (must pass)

Functional

  • Brand create duplicate (case-insensitive) → ConvexError “Brand already exists”.
  • Brand create by non-admin/manager → ConvexError unauthorized.
  • Part create with brand/category persists; part list shows Part Number column header, brand, category cells.
  • Part search with brand=Toyota returns only Toyota rows (and survives q filter).
  • Category filter + brand filter compose (AND).
  • CSV with header “part number” imports; CSV with old “code” still imports.
  • CSV with brand/category columns imports them; missing columns defaults gracefully.
  • Vehicles make picker shows brand suggestions but still allows free-text “CustomBrand 123”.
  • Seed idempotent: re-run seed/seedAdvanced does not duplicate brands/parts.
  • Renaming Code→Part Number: old invoice lines still render original code string (no migration reversal).

Security / correctness

  • parts.create/update/import require inventoryManager|manager|admin; brand CRUD requires admin|manager.
  • Every mutation writes auditLogs entry.
  • Zod trims brand/category; empty string becomes undefined; too-long rejected.
  • Stock immutability not regressed by new fields.
  • No mocked frontend data; query invalidation works after brand/part writes.
